# Explicit prepared registry admission

The ordinary cache loader and ordinary export/startup entrypoints keep their existing behavior. External schema evidence is consumed only through `admit_external_registry` and the explicit prepared entrypoint `run_prepared_with_external_registry`, or its opaque-token form `run_prepared_with_verified_registry`. The generator validates external evidence before its source qualification or session begins. Failed external admission returns an error; it never falls back to extraction or a conventional cache.

Prepared request schema 1 remains unchanged when `external_registry` is absent. Schema 2 requires the explicit descriptor below; its prepared receipt is schema 3 and repeats the same descriptor. The runtime receipt parser preserves and matches that provenance; this does not qualify native/runtime behavior or install a registry.

```json
{"external_registry":{"manifest":{"path":"schema/manifest.json","bytes":123,"sha256":"<approved SHA-256>"},"producer_use_approval":{"path":"schema/producer-use.json","bytes":456,"sha256":"<separately approved SHA-256>"}}}
```

These paths are portable relative names beneath the explicit mod environment. The separately authorized prepared request supplies the trusted exact pins. A status/boolean inside an unbound document is not approval. This verifier is not a cryptographic identity service: the operator must bind the exact request and its evidence pins through the existing canonical/Main acceptance procedure.

The evidence manifest is schema_version 1 with `source_inputs` (the three source stamps), `generation`, and a `files` map. Exact role keys are: registry, identity, report, complete, receipt, adjudication_manifest, ledger, consumer_contract, adjudication_report, adjudication_retention, diagnosis_manifest, matrix, source_evidence, diagnosis_report, diagnosis_decision, diagnosis_retention, actual_refusal, diagnosis_assessment, canonical_acceptance, main_acceptance. Each role has a path/bytes/sha256 pin. Relative paths are checked, aliased names and duplicate JSON keys are rejected, and Windows read handles deny writes/deletion and remain held through the session. Reparse paths are refused. No provenance path embedded in a historical document is followed as an I/O instruction. Initial held-sharing admission is Windows-only and fails closed elsewhere.

The module checks both external data acceptance records, the complete provenance/member graph, exact captured output hashes, the genuine strict extractor identity, source tuple and paired generation. The mandatory report/matrix/ledger/source evidence are retained and hash-verified. It compares every collision pair, owner, replacement sequence and retained winner, the exact record digest/counts, and affected type fingerprints. No wildcard collision approval or raw descriptor/ordinal/native precedence claim is made. Original tool refusal/false qualification remain historical facts.

Final producer use is a DIFFERENT approval from represented-data acceptance. A separately pinned producer-use JSON must declare schemaVersion 1, status COMMITTED_REVIEWED_PRODUCER_EXTERNAL_REGISTRY_USE, sourceState committed, canonicalProducerReviewAccepted/mainProducerUseAccepted true, producerCommit (40 lowercase hex), producer {source_closure, artifact_sha256}, manifestSha256, mainDataAcceptanceSha256, and a canonicalProducerReview path/bytes/sha256 pin. The independently hash-verified producer review must declare schemaVersion 1, status CANONICAL_ACCEPTED_COMMITTED_PRODUCER_SOURCE_ARTIFACT, the same producerCommit, and the same producer identity. Accepted booleans without this bound record are rejected. Both producer fields must match the running producer's compiled HD_PREPARED_SOURCE_CLOSURE and measured executable hash. The data derivation closure remains separate; no own-source equality or extractor alias is allowed. The final approval can only be issued after review, commit and final build; no self-hash is compiled into the producer and no circular source binding is required.

All local test builds use explicitly labeled TESTONLY snapshots for the four existing closure environment variables. They are not final committed producer identities and cannot authorize use of private/current evidence. The final producer closure/artifact/approval and approved prepared request are separate delivery gates. No conventional cache copy/write/relabel or fallback extraction is implemented by this mode. New source freshness, provider/HD preimages, full DAT preparation, generation against actual inputs, native/8K compatibility and installation remain separately authorized operations.

Direct library prepared callers retain the existing responsibility for a startup/source snapshot lease and must supply the same fresh source stamps/root. The generator performs its full existing source qualification after evidence admission and before session use. The session also rejects an external registry whose generation differs from its opened KFC. Evidence admission itself does not renew source freshness.
